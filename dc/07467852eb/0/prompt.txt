### Critical Issues

### High

- **`convex/people.ts:60-72, 80-85` -- `searchPeople` and `getPerson` return full documents, including `embedding` (1536 floats) and `embeddedText`.**
  Cost: each embedded person is roughly 25-30KB of JSON; `searchPeople` re-runs on every keystroke and returns up to 20 docs, so a single keystroke can move ~500KB over the websocket, and the subscription re-fires when a background embed patches any listed doc. The code already knows the right shape -- `fetchSearchResults` (people.ts:212-221) strips exactly these fields for semantic search, so the two search paths are inconsistent with each other.
  Fix: map `searchPeople`/`getPerson` results through the same projection. Longer term, move `embedding`/`embeddedText` to a separate `personEmbeddings` table keyed by `personId` (the guidelines' churn-separation advice), which also stops every embed from rewriting the whole person doc.

- **`src/CaptureTriage.tsx:221-231, 296-300` -- the exit animation dies the moment the query catches up, so the saved card snaps back to center.**
  `isLeaving` requires `leaving._id === topId`. When `acceptCapture` confirms (typically 50-200ms, well inside the 340ms window), the capture disappears from `listCaptures`, `topId` becomes the next card, `isLeaving` flips false, and the `triage-card-exit` class is removed mid-flight. Since `activeTop = leaving ?? top` still renders the old card with no inline transform and the base `.triage-card` has no transition, the card the user just flung off reappears fully opaque at rest until the 340ms timer clears `leaving`. This hits nearly every non-reduced-motion save. The redundant condition on line 224 (`isLeaving || leaving !== null`) is a symptom of the same confusion.
  Fix: gate the exit class on `leaving !== null` (the rendered card is always the leaving card while `leaving` is set), and delete the redundant `isLeaving ||` in `cardStyle`.

- **`src/CaptureTriage.tsx:98-115` -- upload failures are completely silent.**
  `handleFiles` never checks `response.ok`, and the `try/finally` has no `catch`; a failed upload (offline, storage error, non-JSON error body) rejects `Promise.all`, which is `void`ed at the call site (line 244). The "Uploading N..." counter quietly returns to zero and the user believes the screenshot was captured. On mobile networks this is a routine path, not an edge case.
  Fix: check `response.ok` before `response.json()`, catch per-file errors, and surface a "N screenshots failed to upload" state with the count.

### Medium

- **`src/CaptureTriage.tsx:126-146` -- `save()` is optimistic with no failure handling.** `void acceptCapture(...)` swallows rejections, and `savedCount` increments before the mutation lands. If the mutation fails (offline, capture raced into another state), the card flies off, "1 added" shows, and then the same card reappears in the queue -- the UI has asserted a save that never happened. Fix: `.catch` the mutation, decrement/skip the count, and show a brief error; or count saves from the mutation's resolution.
- **`src/CaptureTriage.tsx:316-329, 441-447` + `convex/captures.ts:199-212` -- failed extractions are a dead end, and "Skip" is silently destructive.** A transient OpenAI 500 marks the capture `failed`; the only affordance is "Skip", which permanently deletes the screenshot file and the capture. The file is still in storage, so a retry is nearly free. Fix: add a `retryExtract` mutation (reset status to `pending`, reschedule `internal.captures.extract`) and label the discard action honestly ("Discard") on failed cards.
- **`convex/captures.ts:42-55` and `convex/people.ts:225-261` -- no server-side rate limiting on OpenAI-backed public functions.** `createCapture` triggers a vision call and `semanticSearch` an embedding call; the client debounce is advisory, so any signed-in user with a script can run up the OpenAI bill unbounded. For a public deployment, add a per-user rate limit (e.g. the `@convex-dev/rate-limiter` component) on both entry points.
- **`convex/people.ts:177-184` -- embed failures are silent with no retry.** If the scheduled `embed` action throws (OpenAI down, key missing, context exceeds the embedding token limit), the person simply never appears in semantic search, and nothing ever retries; `backfillEmbeddings` is manual. Fix: schedule a bounded retry with backoff from the action's catch, or run a periodic cron that re-drives people missing embeddings.

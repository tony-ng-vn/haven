The premise "ContactConnector using Composio backend OAuth" is not what the code does.

## 1. Convex data model

### `convex/schema.ts` — the four person-related tables

**`people`** (schema.ts:14-104) — one private row per person the user knows, owned by `userId` (Clerk `tokenIdentifier`). There is **no shared/global person table**; each user's directory is entirely their own rows.

Identity-bearing fields, in three coexisting generations:

| Field | Line | Shape |
|---|---|---|
| `platform` + `handle` (scalars) | 29-30 | Legacy, from screenshot capture. One handle only. |
| `link` | 24 | Free-form string. **The only field that holds a raw URL.** |
| `contactHandles: [{platform, value}]` | 60 | Current structured form. Capped at 8 (`MAX_CONTACT_HANDLES`, people.ts:239), one per normalized platform. |
| `preferredPlatform` | 64 | Must name a platform present in `contactHandles`. |

Other fields: `name`, `normalizedName`, `context` (the user's note), `city`/`cityKey`, `company`/`companyKey`, `role`/`roleKey`, `headline`, `bio`, `photoStorageId`, `screenshotId`, `embedding`/`embeddedText`, `searchText`, `havenContactUserId`, `connectionEndedAt`.

**`personHandles`** (schema.ts:135-146) — the scalar identity index behind the array. Convex cannot index inside arrays, so `{userId, personId, platform, valueKey}` rows are maintained in the same transaction as every `contactHandles` write. Index `by_user_and_platform_and_valueKey` is the dedup key for the whole system.

**`connections`** (schema.ts:150-161) — mutual, both-sides-consented Haven-user links: `{userAId, userBId, personAId, personBId, status: "connected"}`. Each side keeps its own private `people` row; this row is only the access gate for `sharedNotes`.

**`profiles`** (schema.ts:218-243) — the user's *own* card. `handles: [{platform, value, verified}]` where `platform` is a **closed union**: `instagram | x | linkedin | phone` (`profileFields.ts:9-14`). Email is deliberately excluded (comment at profileFields.ts:7-8).

**`memories`** (schema.ts:112-129) — one row per line of `people.context`, with its own vector.

### Handles are bare usernames, not URLs, not structured objects

`convex/handleKeys.ts` is the single folding seam:
- `handleDisplayValue` (line 10-12): trim, strip leading `@`.
- `handleValueKey` (line 17-19): the above, lowercased. Comment: *"Deliberately naive in v1; per-platform rules can grow here later."*
- `handleIndexKeys` (line 24-35): platform trimmed + lowercased, value → `valueKey`.

So `instagram/mai.makes` is stored as `value: "mai.makes"`, `valueKey: "mai.makes"`. URLs are **reconstructed at render time**, never stored as identity.

### Two asymmetries in the schema

1. **Platform vocabulary**: `profiles.handles.platform` is a closed union of 4; `people.contactHandles.platform` is free-form `v.string()` (`peopleFields.ts:11-14`, comment: *"platform is free-form on purpose... WhatsApp and Telegram included"*).
2. **Provenance**: `profiles.handles` carries `verified: boolean`; `people.contactHandles` has **no `verified` field at all**. On the profile side only X ever sets it true, because X returns the username with the token while LinkedIn does not (`profileFields.ts:16-18`, `ContactScreen.swift:186-194`).

## 2. iOS Contacts capability

### The shipping iOS app has none

Grep for `CNContact`, `CNContactStore`, `import Contacts` across `ios/Haven`, `ios/HavenTests`, `ios/HavenShare`, `ios/HavenWidget` returns **zero hits**. The only files matching "Contact" are `ContactConnector.swift`, `ContactScreen.swift`, `ContactValue.swift` — all about the onboarding "how should people reach you?" question, not the address book.

`ios/Haven/Info.plist` declares exactly one usage description: `NSCameraUsageDescription` (line 32). No `NSContactsUsageDescription`.

### What ContactConnector actually does

`ContactConnector.connect(_ provider:)` (ContactConnector.swift:34-59) links an external account to the signed-in Clerk user, in three cases: already-verified → return it with no browser trip; half-linked → `prepareReauthorization()`; nothing yet → `createExternalAccount`. Returns `ConnectedAccount { username: String?, fullName: String, imageUrl: String? }` (lines 5-13), built from Clerk's `ExternalAccount.username / firstName+lastName / imageUrl`.

Consumed by `ContactScreen.finish` (ContactScreen.swift:176-196): the avatar URL is handed to `model.rememberAvatar`; the username is accepted as a handle **only if the platform proves it** (`provesItsHandle: true` for X, `false` for LinkedIn). LinkedIn falls through to `degrade`, which prefills a guessed slug from the proven name (`ContactValue.linkedInSlug`, ContactValue.swift:63-71) for the user to correct. Instagram is `.typed` — no OAuth attempted at all, because Clerk offers no Instagram connection (ContactScreen.swift:265-272).

That is the entire scope: **one handle for the user's own card**. It pulls no contact list, no phone numbers, no address book.

### The Contacts work is in `graph/`, a separate non-shipping macOS package

`graph/` is a standalone SwiftPM package (`graph/Package.swift`) plus a macOS app (`graph/App/project.yml`). `graph/GOAL.md` describes it as *"a personal tool with exactly one user, never distributed"* and constraint 5 forbids it from touching `convex/`, `src/`, `ios/`, or root config. `graph/App/project.yml:60-62` records that it deliberately ships with **no entitlements file and no App Sandbox**, because Full Disk Access cannot be granted to a sandboxed app.

- `graph/Sources/GraphCore/ContactsDatabase.swift` reads `AddressBook-v22.abcddb` via **raw read-only SQLite**, not `CNContactStore`. It queries `ZABCDRECORD` (filtered by the `ABCDContact` entity id looked up in `Z_PRIMARYKEY`), `ZABCDPHONENUMBER.ZFULLNUMBER`, `ZABCDEMAILADDRESS.ZADDRESS`, producing `ContactRecord{recordID, uniqueID, firstName, lastName, organization, nickname, phoneNumbers, emails, thumbnailImageData}`.
- `graph/Sources/GraphCore/AccessProbes.swift:33-63` — `ContactsPathDiscovery` finds *multiple* stores: top-level `~/Library/Application Support/AddressBook/AddressBook-v22.abcddb` plus one per linked account under `Sources/&lt;id&gt;/`.
- `graph/Sources/GraphCore/IdentityResolution.swift` is a union-find over normalized identifiers (details in §4).

## 4. What the design docs decided about cross-platform identity

### `docs/2026-07-30-imessage-connection-graph-research.md` (726 lines, "research complete, no decision made")

- **Central recommendation** (lines 52, 474): *"Import the people. Do not persist the graph server-side."* The people are defensible; the edges are a separate processing operation that 2009 EU guidance said lacks a legal basis, and that drags toward GDPR Art. 9.
- **On merging** (lines 264-267): *"On uncertain matches, never auto-merge. Auto-merge only exact normalized-identifier equality. Everything probabilistic goes to a confirmation queue, implemented as a non-destructive link with provenance so unlinking is lossless, which is the pattern Apple Contacts uses."* Rationale: a wrong non-merge costs a duplicate row; a wrong merge blends two humans' notes.
- **Apple's own cross-handle key is unusable** (line 257-259): `person_centric_id` in `chat.db` is Apple's cross-handle clustering key, but the maintainer of the most mature open-source exporter found it empty in 100% of polled databases. *"Treat any value present as an opportunistic hint, never as authority."*
- **Phone normalization** (line 261-262): `chat.db` stores handles already E.164-canonicalized at write time. *"The messy side is our own saved handles and Contacts entries, where libphonenumber via PhoneNumberKit with the device region handles most of it."*
- **Explicit self-correction about the current schema** (lines 612-621): *"`people.contactHandles` is an array of `{platform, value}` where the value is the raw handle, and `personHandles` mirrors every one of them as an indexed `valueKey` row. Convex holds the phone numbers and email addresses of non-consenting third parties **today**."*
- **`personHandles` named as the cross-user primitive** (line 388): *"The `personHandles` index on normalized handles is exactly the primitive that enables querying across the `userId` boundary."*
- **Cross-user correlation ruled out** (§4): fails on Apple guideline 5.1.2(iv)/(iii), on cryptography (PSI is a protocol between parties who already decided to compare; hashing phone numbers is an encoding, reversed at 0.1 ms in NDSS 2021), and on precedent (Path, Buzz, PYMK, Clubhouse, Covve). The one form with a clean record is LinkedIn-style mutual confirmation — *"which Haven already has"* in the `connections` table (lines 356-364).
- **Not building** (line 653-659): 3rd degree; cross-user correlation; server-side derived edges; visible closeness scores; bulk invite.

### `docs/2026-07-31-polygres-network-design.md` (214 lines, "proposed, nothing applied")

Proposes a Postgres (Polygres) **read model** synced from Convex for agent retrieval; Convex stays system of record and the UI never reads Polygres. Mirrors `people`, `person_handles` (with `unique (user_id, platform, value_key)` — line 103), `memories`, `connections`, plus a new `person_edges` table (`kind`: `same_company | same_city | introduced_by`, `source`: `derived | manual | import`), empty at launch. Line 24-26 explicitly fences off the iMessage graph. Line 52: *"Fuzzy: not configured now. Names arrive normalized (`normalizedName`, `valueKey`); add trigram matching only if typo-miss becomes an observed problem."*

### `graph/PLAN.md` + `graph/Sources/GraphCore/IdentityResolution.swift` (the only implemented identity resolution)

Rules, implemented as union-find over normalized identifier strings:
- **Rule 1**: two handles normalizing to the same string are the same person (falls out for free — equal strings are the same node).
- **Rule 2**: identifiers **co-listed on one contact card** are the same person (IdentityResolution.swift:89-103). A card naming both a phone and an email is the join evidence.
- **Rule 3**: user-asserted merges from the override store, applied as extra unions (lines 112-114).
- **Contacts never creates a node** (PLAN.md:108) — a card only *attaches* to a person that messages created. (Amended 2026-08-03 to let never-messaged contacts appear as hollow, inference-excluded rings.)
- **Same-name pairs are never auto-merged** — they become `MergeCandidate{personID1, personID2, sharedName}` for a human queue (IdentityResolution.swift:42-54, 195-211), and answers persist as `MergeAnswer{identifierA, identifierB, decision: merged|separate}` in `Overrides.swift:17-32`.
- **Overrides key on normalized identifier, never row id** (PLAN.md:91), because row ids renumber across resync.
- `Person.id` is the lexicographically smallest normalized identifier, with a documented instability: attaching a new card can introduce a smaller phone number and shift the id (IdentityResolution.swift:6-12).
- `HandleNormalization.normalize` (HandleNormalization.swift:24-35): contains `@` → `.email(lowercased)`; else E.164-ish phone with a **hardcoded US `+1` default** for 10-digit and leading-1 11-digit strings; else `.other(unchanged)`. Comment: a non-normalized phone *"merely fails to merge later, one duplicate node, which PLAN.md prices far cheaper than a wrong merge."*
- Same-name collisions get a masked-suffix disambiguator (last 4 chars of identifier) at display time only (PLAN.md:134-136).

### Other docs

`mvp-design.md:141,151,191` is the cited authority for the platform asymmetry (own card = 4 platforms; a saved person = any handle, WhatsApp and Telegram included) and for "if the person is a connected Haven user, the contact holds a reference to their live profile and the app renders the merge." ## 6. Gaps observed, mapped to the three areas

### (a) Looking up an Apple contact by phone number

- The shipping iOS app has no Contacts framework code, no `NSContactsUsageDescription`, and no phone-number-to-contact lookup anywhere.
- The only address-book reader is `graph/Sources/GraphCore/ContactsDatabase.swift`, a **macOS raw-SQLite** reader in a package that is by charter forbidden from touching `ios/` and by build config unsandboxed. It reads `ZFULLNUMBER` raw and keys by owner row — there is **no phone → contact reverse index**; the caller iterates records.
- **Three different phone normalizers write into the same `valueKey` column**: `ContactValue.phoneNumber` uses PhoneNumberKit with the *device* region (ContactValue.swift:78-81); `graph`'s `HandleNormalization.normalizedPhone` hardcodes a US `+1` default (HandleNormalization.swift:39-57); `reach.ts` keeps a web-entered number **exactly as typed** (line 194). `reach.ts:185-189` states the consequence outright: *"the two platforms do still disagree on the stored string, so a person saved on both makes two keys rather than one. That is a real gap and closing it needs a phone library here, not a regex."*
- `handleValueKey` (handleKeys.ts:17-19) is trim + strip-`@` + lowercase only — it applies no phone normalization at all.

### (b) Attaching a new social profile to an existing person vs creating a new one

The write paths disagree, and the code documents the disagreement:

1. `addPerson` (people.ts:356-427) inserts unconditionally; its handler never touches `by_user_and_platform_and_valueKey`.
2. `editPerson` (people.ts:847-897) rewrites `contactHandles` and re-inserts `personHandles` with no cross-person check.
3. `saveSharedProfile` (people.ts:998-1006) reads that index with **`.unique()`**. The comment above it (people.ts:992-997) records the trade: *".unique(), not .first(): two owners of one handle is corruption… Production reported zero duplicate handle owners on 2026-07-28… **addPerson still imposes no global uniqueness, so this can throw on a directory the owner built by hand** — see that plan's B3 for the trade."*
4. Therefore a web add (`SearchAdd.tsx:320`) or an iOS handle-add through `editPerson` can create two owners of one `(userId, platform, valueKey)`. A subsequent share, or an iOS manual add on that handle, hits `.unique()` and throws — and because iOS manual add drains through `saveSharedProfile` (`ConvexCaptureSink.swift:77`), that queued capture cannot drain.
5. `reportDuplicateHandleOwners` (people.ts:1984-2076) is the detector for exactly this state. Its header comment: *"Report only, never a merge: which of two people holding one account is the real one is a decision only the user can make."*
6. **There is no merge mutation in `convex/`.** `mergePeerHandles` (people.ts:649) merges a *connected peer's live card* into the read projection of the detail screen; it is not a person-merge. `deletePerson` is the only way to collapse duplicates, and it takes the memories with it.
7. `saveSharedProfile`'s attach path itself falls through to **create** when the target already holds a *different* account on the same platform (people.ts:1063-1067): *"the capture falls through to create rather than strand the queued item; the user can merge the twins later"* — a merge that does not exist server-side.
8. Web has no attach affordance at all (`PersonDetail.tsx` renders handles read-only; only iOS's `PersonHandlesEditor` can add a handle to an existing person, via `editPerson`).
9. `graph/` has the merge machinery Haven lacks — `MergeCandidate`, `MergeAnswer{merged|separate}`, `MergeQueueView.swift`, `MergeCandidateSuppression.swift`, union-find over co-listed card identifiers — but it is a separate, non-distributed macOS tool with no server component.

### (c) Social profile URLs going stale when usernames change

- Nothing stores a URL as an identity key; `contactHandles.value` is a bare username and `valueKey` is its lowercase fold. URLs are rebuilt at render (`reachUrl`, `ProfileURL`, `AddPersonPlatform.profileUrl`, `deriveProfileUrl`).
- The one raw-URL store is `people.link` (schema.ts:24), and `linkBackfill` (people.ts:333-341) **never overwrites an existing link** by design: *"An existing link is never overwritten: the user chose that one."* Once set, it persists unchanged.
- Nothing ever re-fetches or re-verifies a handle. `ProfileURL.swift:28-29`: *"Pure and offline by design: the URL is a pointer, never fetched, and the extension does no network at all."*
- `people.contactHandles` carries **no `verified` field** (peopleFields.ts:11-14), so a person-level handle has no recorded provenance — no way to distinguish an OAuth-proven handle from a guessed LinkedIn slug. Only `profiles.handles` has `verified`, and only X ever sets it true (ContactScreen.swift:186-194).
- Consequence chain: a username change means `reachUrl` keeps building the dead address indefinitely, and a re-share under the *new* username misses `by_user_and_platform_and_valueKey` entirely and creates a **second person** — which lands back in gap (b) with no merge path.
- `reach.ts:23-27` shows the one form of staleness that *is* handled: `twitter` is kept as a readable-but-not-offerable alias for `x`, *"because rows written before the rename still say twitter, and the person behind them has not moved."* That is platform-rename tolerance, not username-change tolerance — and it means `platform: "twitter"` and `platform: "x"` are two distinct `valueKey` namespaces for one account.
- `handleValueKey`'s comment (handleKeys.ts:16) flags the extension point: *"Deliberately naive in v1; per-platform rules can grow here later"* — e.g. Instagram treats dots as significant while Gmail does not, and none of that is modeled.</result>

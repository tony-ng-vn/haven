## 1. Files changed and why

Backend (Convex):
- `convex/schema.ts` — removed `authTables` (Convex Auth's `users`, `authAccounts`, `authSessions`, etc.) and its spread into the schema. Changed `people.userId` and `captures.userId` from `v.id("users")` to `v.string()`, since ownership is now keyed on Clerk's `tokenIdentifier` string, not a local user document.
- `convex/auth.config.ts` — provider domain now reads `process.env.CLERK_JWT_ISSUER_DOMAIN` (was `CONVEX_SITE_URL`), `applicationID: "convex"` unchanged (matches the JWT template name).
- `convex/auth.ts` — deleted. This was Convex Auth's `convexAuth({ providers: [Password] })` setup; nothing in Clerk needs an equivalent.
- `convex/http.ts` — deleted. Its only content was `auth.addHttpRoutes(http)`, Convex Auth's Password-provider callback routes. Clerk's client SDK verifies JWTs directly; no Convex HTTP routes are needed.
- `convex/people.ts`, `convex/captures.ts` — `getAuthUserId(ctx)` replaced with a `requireUser()` helper that calls `ctx.auth.getUserIdentity()` and returns `identity.tokenIdentifier` (the guidelines file explicitly prefers `tokenIdentifier` over the bare `subject` claim for ownership checks). All existing ownership logic (`person.userId !== userId`, etc.) is unchanged, just fed a string from a different source.
- `convex/people.test.ts`, `convex/captures.test.ts` — `asNewUser()` no longer inserts into a `users` table (deleted). It mints a fake Clerk identity and calls `t.withIdentity({ subject, issuer })`; convex-test synthesizes `tokenIdentifier` the same way Convex does in production (`"issuer|subject"`).
- `convex/_generated/api.d.ts` — hand-patched to drop the `auth`/`http` module entries (see caveat below).

Frontend:
- `src/main.tsx` — `ConvexAuthProvider` replaced with `ClerkProvider` (publishable key from `VITE_CLERK_PUBLISHABLE_KEY`) wrapping `ConvexProviderWithClerk` (from `convex/react-clerk`, `useAuth` from `@clerk/react`).
- `src/App.tsx` — the hand-rolled email/password form (`useAuthActions`, flow/error/shake state) is replaced by `&lt;SignInButton mode="modal"&gt;` around a `.btn-primary` button inside the existing `.auth`/`.auth-card` shell. ## 2. Manual steps you need to do

1. In the Clerk dashboard, create an application (or use an existing one).
2. In that Clerk app, go to **JWT Templates** and create a new template named exactly **`convex`** (the name must match `applicationID: "convex"` in `convex/auth.config.ts`).
3. Note the app's **Frontend API URL** (issuer domain), shown in Clerk's dashboard — looks like `https://verb-noun-00.clerk.accounts.dev`.
4. Set env vars in three separate places — do not mix these up, they are not interchangeable:
   - **Convex deployment** (dashboard -&gt; Settings -&gt; Environment Variables, or `npx convex env set CLERK_JWT_ISSUER_DOMAIN https://your-app.clerk.accounts.dev`): `CLERK_JWT_ISSUER_DOMAIN`. This is server-side only; it must NOT go in Vercel or any client env.
   - **Local `.env.local`** (copy from `.env.local.example`): `VITE_CLERK_PUBLISHABLE_KEY` (from Clerk dashboard -&gt; API Keys -&gt; Publishable key, `pk_test_...` or `pk_live_...`). Client-safe.
   - **Vercel** (project env vars): same `VITE_CLERK_PUBLISHABLE_KEY`, plus a redeploy after setting it (Vite bakes `VITE_*` vars in at build time).
5. Run `npx convex dev` (or `deploy`) once, authenticated against the linked Convex deployment, so it picks up the schema/auth.config changes and regenerates `convex/_generated/` cleanly from source (I hand-patched `api.d.ts` locally since this sandbox has no linked deployment — see caveat below).
6. Sign in through the app once with a real Clerk account to confirm the JWT round-trips end to end; this path is unverified by me since I have no real keys.

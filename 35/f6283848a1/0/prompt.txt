## MUST HAVE

### 1. Minimal CI running the suite (effort: ~30 min)

The single highest-leverage item. Vercel's build (`npx convex deploy --cmd 'npm run build'` in `vercel.json`) gives you typechecking at deploy time, but the 42 tests never run on push or PR. A regression net that never runs catches nothing. The suite finishes in half a second, so cost is trivial.

Minimal workflow (`.github/workflows/test.yml`):

```yaml
name: test
on:
  push: { branches: [main] }
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npm test
      - run: npm run build
```

`npm run build` is safe in CI (it is `tsc -b &amp;&amp; vite build`, no deploy, no env vars needed) and adds typechecking of `src/` and `convex/`. Do not add coverage thresholds -- that creates the padding incentive this project explicitly avoids.

### 2. Triage race and double-action tests, server side (effort: ~45 min, existing harness covers all of it)

The capture pipeline's data integrity under concurrent/racing actions is the core of the app, and none of it is tested:

- **Skip while still reading.** The UI shows Skip for a pending card, so "discard while extraction is running" is a normal user flow, and `finishExtract`/`failExtract` in `/Users/minhthiennguyen/Desktop/Euno/euno-app/.worktrees/feat-clerk-auth/convex/captures.ts` carry explicit null guards for exactly this race -- with zero tests. Test: `createCapture`, `discardCapture` *before* `finishAllScheduledFunctions`, then finish scheduled functions and assert nothing throws and no capture/person exists. Also call `internal.captures.finishExtract` directly with the deleted id to pin the guard itself. Catches: someone "simplifying" away the null guards, which would turn a routine skip into a crashing scheduled function.
- **Double accept.** `acceptCapture` twice on the same capture: second call must throw "Capture not found", not create a duplicate person. Catches: the no-duplicate-person invariant on rapid double-tap (the client currently *can* double-fire, see finding below).
- **Accept a non-ready capture.** `acceptCapture` on a pending or failed capture must throw "Capture is not ready". The UI guards this but the mutation is public API; the status check is the only thing preventing a person row with garbage data.

### 4. Fix two weak spots in existing tests (effort: 15 min)

- **"bumps updatedAt" verifies nothing.** In `/Users/minhthiennguyen/Desktop/Euno/euno-app/.worktrees/feat-clerk-auth/convex/people.test.ts` line 104, `expect(after!.updatedAt).toBeGreaterThanOrEqual(before!.updatedAt)` passes even if the mutation never touched `updatedAt` at all (equal values satisfy `&gt;=`). Use fake timers to advance the clock between create and update, then assert strictly greater. This is the one existing test that passes while proving nothing about its own name.
- **stubOpenAI silently falls through to the real network.** In `captures.test.ts`, the fetch stub routes on URL substrings and passes everything else to the real `fetch`. Make any unmatched `api.openai.com` URL throw loudly instead of falling through. This is the fragile-mocking pattern in the suite; everything else about the mocking (stub at the network boundary, not between internal functions) is right.

## NICE TO HAVE

### 5. Embed idempotency (effort: 20 min)

`embedPerson` in `convex/people.ts` deliberately skips re-embedding when `embeddedText` is unchanged -- there is even a comment calling the stored text an idempotency key -- but no test. Add a fetch-call counter to the stub: update a person with identical values, assert the embeddings endpoint was hit exactly once. Catches a regression that silently multiplies OpenAI cost and latency; it would never show up as a functional failure.

### 6. Extraction response edge cases (effort: 15 min)

- Model returns a refusal / no `choices` -&gt; capture fails with "OpenAI returned no extraction" rather than a raw TypeError message surfacing to the user.
- `is_profile: true` but `name: null` or `""` -&gt; "Could not read a profile in this screenshot" (the tested case only covers `is_profile: false`; the empty-name branch in `extractProfile` is separate input territory).

I would *skip* a malformed-JSON-content test: with `strict: true` json_schema mode the model cannot emit non-JSON, and the failure would land in the same generic catch the 500-error test already covers. Testing it adds a case, not confidence.

### 7. semanticSearch empty branches (effort: 10 min)

Two untested early returns: blank query -&gt; `[]` without calling OpenAI (assert no fetch), and all-matches-below-threshold -&gt; `[]`. Cheap, and the second pins the `MIN_SEMANTIC_SCORE` gate as a standalone behavior instead of only implicitly inside the happy-path test. Embed-failure (OpenAI down) server-side is not worth testing -- the action just propagates, and the meaningful behavior (silent degradation) lives in the client.

## NOT WORTH TESTING (explicitly)

- **PersonSky rendering.** Purely presentational; all logic lives in `buildSky`, which is tested. An SVG snapshot test is exactly the padding the project rules prohibit.
- **App auth gating.** `Authenticated`/`Unauthenticated`/`AuthLoading` composition is Convex's framework behavior. The one piece of app logic (`isClerkFlowHash`) is already extracted and tested -- the right call was already made here.
- **RTL component tests for SearchAdd / PersonDetail / CaptureTriage.** The bugs they would guard are real (stale semantic results despite the cancelled-flag, live query clobbering in-progress typing despite the dirty flag, double-tap Save), but the setup cost is nontrivial: new deps (`@testing-library/react`, `happy-dom`), plus per-file environment config since the Convex tests need `edge-runtime`. Defer until one of those areas actually churns or bites; extract-and-unit-test (items 8-9) buys most of the value for none of the infrastructure.
- **Unicode/diacritic search through convex-test.** Whether Convex's production full-text search matches an ASCII query against a Vietnamese name with diacritics is platform behavior that convex-test's simulator may not reproduce faithfully -- a green test would be false confidence. Do a one-time manual check on the real deployment; if ASCII-folding matters for the product, that becomes a normalization feature (with tests), not a test of the simulator. The rest of the unicode surface is safe by inspection: `hashString` handles any UTF-16 input deterministically, and `buildEmbedText` is plain string assembly. NFC/NFD normalization differences are theoretically possible across input sources but have no user-visible consequence given skies are per-record.

## Code findings surfaced while evaluating (not test gaps, but worth relaying)

1. **Double-tap Save fires twice.** `save()` in `src/CaptureTriage.tsx` calls `void acceptCapture(...)` with no catch and no in-flight guard, and increments `savedCount` optimistically. A rapid second tap throws "Capture not found" as an unhandled rejection and over-counts. Fix is a guard/disabled state; the must-have server test (item 2) pins the invariant that matters (no duplicate person) in the meantime.
2. **`handleFiles` ignores upload failure.** `response.json()` is called without checking `response.ok`; a failed storage upload becomes an opaque crash inside the void'd promise.
3. **Unbounded context length silently breaks semantic search.** Nothing caps the context textarea. A very long context makes `embedText` fail (embedding model input limit), the scheduled embed action dies silently, and the person is saved but permanently invisible to semantic search -- no error anywhere. Consider truncating the embed text or capping input, then test the cap.
